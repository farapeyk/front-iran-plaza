# راهنمای توسعه و QA

## افزودن یا تغییر قابلیت

۱. مسیر صفحه را در `src/app` و منطق آن را در feature مربوط قرار دهید. Route Group را از URL نهایی جدا در نظر بگیرید.
۲. دریافت داده سرور، تعامل کلاینت و mutation را مطابق الگوی موجود تفکیک کنید. secret و token نباید به bundle مرورگر برسند.
۳. ورودی untrusted را در مرز Server Action یا بک‌اند اعتبارسنجی کنید؛ typeهای TypeScript به‌تنهایی کافی نیستند.
۴. stateهای ارسال، خطا، خالی و موفقیت را مشخص کنید. خطای شبکه را بدون تصمیم محصول به «داده وجود ندارد» تبدیل نکنید.
۵. مجوز backend، مالکیت شناسه‌ها، refresh و قرارداد پاسخ را بررسی کنید. مخفی‌کردن منو مجوز امنیتی ایجاد نمی‌کند.
۶. route، مدل یا endpoint تغییرکرده را در اسناد مربوط به‌روز کنید.

برای onboarding، ترتیب را از `PROFILE_STEPS` بخوانید. تغییر تعداد مراحل نیازمند بررسی بازه پاسخ helper، redirectها، وضعیت داده موجود و قرارداد بک‌اند است. برای فایل، الگوی upload سپس ثبت fileId را رعایت کنید و شکست نیمه‌کامل را در UI پوشش دهید.

## بررسی خودکار موجود

```powershell
npm run lint
npx --no-install tsc --noEmit --incremental false
npm test
npm run build
```

suite فعلی علاوه بر onboarding، ورودی‌های mutation، تاریخ، upload، JWT، کوکی، redirect، ناسازگاری دسته و HTTP fixture و مستندات را کنترل می‌کند. تست ثبت از fetch و cookie mock استفاده می‌کند؛ تست HTTP جدید loopback واقعی دارد اما بک‌اند آن fixture است؛ هیچ دیتابیس، SMS یا حساب واقعی را تست نمی‌کند. برای تغییر رفتار، regression معنادار اضافه کنید و پوشش موجود را جایگزین E2E تلقی نکنید.

| عمومی | جستجو، فیلتر، صفحه‌بندی، slug ناموجود، خطای backend و لینک‌های فایل |

برای سناریوهای واقعی از حساب و داده آزمایشی و محیط ایزوله استفاده کنید. schema یا migration این فرانت‌اند ندارد؛ بررسی migration بک‌اند باید جدا و روی دیتابیس ایزوله انجام شود.

## سیاست قبل از commit

طبق دستور کاربر و [چک‌لیست موجود](QA-SPECIALIST-CHECKLIST.md)، قبل از هر commit، merge یا amend، diff دقیق staged، وضعیت و whitespace بررسی می‌شود:

```powershell
git status --short
git diff --cached
git diff --cached --check
```

تغییرات نامرتبط، secretها و خروجی‌های تولیدشده را وارد commit نکنید. برای تغییر runtime، build/type check و suite مرتبط روی محتوای نهایی لازم است. تغییرات قرارداد به پنج کنترل [سند API](API-AUTH.md) نیاز دارند. نتایج mock، واقعی، skipped و blocked را جدا گزارش کنید. با شکست یا مسدودبودن کنترل الزامی commit نکنید مگر waiver صریح کاربر ثبت شده باشد.

برای تغییر صرفاً مستندات، محتوای فنی، مسیرها، لینک‌ها، encoding و diff بررسی می‌شوند؛ build و E2E فقط برای چنین diffی لازم نیستند، چون رفتار اجرایی تغییر نکرده است. تست‌هایی که برای بررسی وضعیت مبنا اجرا می‌شوند باید با همین عنوان گزارش شوند.

## نگهداری مستندات

با افزودن/حذف page یا handler، `ROUTES.md` و `SOURCE-MAP.md` را به‌روز کنید. با تغییر API و auth، `API-AUTH.md`؛ با تغییر ثبت و پیشرفت، `BUSINESS-ONBOARDING.md`؛ و با تغییر script/env، `SETUP.md` را اصلاح کنید. گزارش قدیمی را به عنوان اثبات QA جدید بازنشر نکنید؛ تاریخ، فرمان و محدودیت هر بررسی را ثبت کنید.
