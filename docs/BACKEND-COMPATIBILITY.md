# سازگاری لازم بک‌اند

این سند حاصل تطبیق فرانت با سورس **محلی** بک‌اند در ۲۰۲۶-۱۰-۰۷ است. بک‌اند در این کار تغییر نکرده و نسخه سرور در دسترس نبوده است.

به‌روزرسانی بررسی صفحه مدیر: سرویس اکنون پاسخ می‌دهد؛ Swagger زنده endpoint پیشرفت onboarding را دارد، درحالی‌که سورس محلیِ بررسی‌شده آن را نداشت. بنابراین اختلاف‌های زیر، اختلاف سورس محلی هستند و نبود قابلیت در سرور را ثابت نمی‌کنند. `/api/plans` در درخواست تازه ۴۰۴ داد؛ اثر آن روی صفحه مدیر در [گزارش اصلاح](ADMIN-BUSINESS-DETAIL-FIX.md) ثبت شده است.

## موارد تأییدشده در سورس

- `FileAssetController`: upload multipart با `file` و سقف ۲۰MB؛ GET فایل با کنترل عمومی/خصوصی و مالک/مدیر.
- `NotificationController`: هر دو `/notifications` و `/api/notifications` پشتیبانی می‌شوند.
- `CreateServiceDto`: نام مدت `durationMin` است.
- `SocialMediaDto`: instagram، telegram، whatsapp و website.
- فهرست admin کسب‌وکار: فیلتر status و response دارای data/total/skip/take.
- امضای access token با secret مشترک انجام می‌شود؛ فرانت HS256 و claimهای ضروری را کنترل می‌کند. issuer/audience در قرارداد محلی تعریف نشده و مقدار حدسی اضافه نشده است.

## اختلاف بسته onboarding

فرانت `onboardingStep` و POST `/api/businesses/{id}/onboarding/advance` را مصرف می‌کند، ولی در سورس محلی controller/schema موجود نیستند. UpdateBusinessDto نیز categoryIds و مسیر ذخیره رابطه دسته‌ها را ندارد. برای فعال‌شدن کامل این امکانات:

۱. بک‌اند مطابق بسته onboarding باید فیلد عدد صحیح با بازه ۰ تا ۱۱، پیش‌فرض سازگار برای داده قدیمی و مقدار صفر برای ثبت جدید کاربر داشته باشد.
۲. endpoint پیشرفت باید مالکیت، ترتیب، مقدار step و تکرار درخواست را کنترل و `{onboardingStep}` معتبر برگرداند.
۳. PATCH کسب‌وکار باید categoryIds را اعتبارسنجی و رابطه دسته‌ها را با کنترل فعال‌بودن و Tenant، به‌صورت تراکنشی ذخیره کند؛ پاسخ باید دسته‌های ذخیره‌شده را شامل شود.
۴. migration و داده موجود باید در دیتابیس ایزوله آزموده شوند؛ این فرانت migration بک‌اند ایجاد نکرده است.

فرانت اکنون پاسخ ناقص را موفقیت تلقی نمی‌کند؛ پس از ذخیره جزئیِ مشخصات و رد/نادیده‌گرفتن دسته، پیام توضیحی می‌دهد. این کنترل جای پیاده‌سازی backend را نمی‌گیرد.

## کنترل قرارداد پیش از استقرار

| کنترل | وضعیت این بررسی |
| --- | --- |
| تولید schema کامل با strict validation، نام‌های پایدار و baseline مرورشده | انجام نشده؛ فرمان/schema/baseline رسمی در فرانت وجود ندارد و سرویس زنده در دسترس نیست. |
| درخواست واقعی به URLهای تولیدشده فایل | با حساب و فایل واقعی انجام نشده؛ مسیر از controller تأیید شده است. |
| فیلد multipart binary در schema تولیدشده | انجام نشده؛ سورس `FileInterceptor` به‌تنهایی اثبات schema نیست. |
| نوع و required بودن path parameter در schema | انجام نشده؛ typeهای دستی فرانت جای قرارداد تولیدشده نیستند. |
| پاسخ‌های خطای کسب‌وکار و فیلدهای DTO در schema | انجام نشده؛ رفتار محلی فرانت تست شده است، نه schema زنده. |

در مرحله قبلی، درخواست خواندنی به categories، plans، فهرست businesses و notifications در مقصد پیکربندی‌شده تلاش شد و اتصال در دسترس نبود. در بررسی تازه صفحه مدیر، Swagger قابل دریافت بود و plans پاسخ ۴۰۴ داشت. هیچ درخواست تغییردهنده به آن سرویس یا دیتابیس ارسال نشده است. تست fixture HTTP جدا از این کنترل‌هاست.
